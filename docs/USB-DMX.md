# USB-DMX: варианты адаптеров и интерфейс FontanPlay

Справочник по выводу DMX через USB. Задачи по этой теме — в `IDEAS.md`,
памятка для человека на объекте — в `USB-DMX-проверка-на-объекте.md`.

## Три варианта и чем они отличаются

**Главное: у всех трёх внутри микросхема FTDI и один и тот же драйвер FTDI.**
Различает их не «FTDI или не FTDI», а то, **что программа шлёт** в эту
микросхему. Поэтому по Диспетчеру устройств их не отличить (все — COM-порт,
VID 0403), только по самому адаптеру и по выбранному в программе протоколу.

| Вариант | Что внутри | Что шлёт компьютер |
|---|---|---|
| **ENTTEC PRO** | FTDI + свой контроллер | кадр в обёртке ENTTEC; тайминг линии держит адаптер |
| **Open DMX** | FTDI, контроллера нет | сырой DMX сам: BREAK, MAB, 250 кбит/с 8N2 |
| **FountanPlay** | FTDI FT245R + контроллер PIC | кадр в обёртке FontanPlay; тайминг держит интерфейс |

- У **Open DMX** весь кадр строит компьютер, а таймеры Windows грубые
  (~1–16 мс): паузы выходят длиннее нужного (стандарт это допускает), но под
  нагрузкой ПК возможны рывки. Опто-развязки обычно нет — на фонтане с насосами
  не ставить.
- **Приборы на линии** (LED-диммеры, свитчеры клапанов, преобразователи в
  0–10 В для ПЧ) — обычные приёмники DMX512 с адресом на DIP. Им всё равно, кто
  источник сигнала.
- **Что ставить на объектах с оборудованием FontanPlay:** менять ничего не
  нужно — выбрать «USB-DMX (FountanPlay)» и работать через тот же интерфейс
  (FontanPlay на это время закрыть). На новых объектах по-прежнему лучше узел
  Art-Net/sACN с развязкой в щите.

## Интерфейс FontanPlay: что снято с программы

Разобрана рабочая версия пользователя **FontanPlay 1.9.2.4** (16.09.2026).
Файлы из FP_60_years, FP_5by5_Abkhazia, F_DEN_POBEDY и SAKI_FULL **побайтово
одинаковы** (md5 15c2aa7d…, 2 930 176 Б) — один формат покрывает все объекты.

- Порядок работы: открыть ПЕРВОЕ FTDI-устройство `FT_Open(0)` →
  `FT_ResetDevice` → `FT_SetTimeouts(500, 500)` → дальше только `FT_Write`.
  Ни скорости, ни BREAK, ни чтения: сигнал DMX на линии строит микроконтроллер
  интерфейса.
- **Кадр на один выход (518 байт):**
  `FF FF FF` (метка начала) + `<выход>` + `00` (стартовый код DMX) +
  512 байт каналов (значение 255 передаётся как 254) + `FF` (метка конца).
  Длина сверена по аргументу `FT_Write`: программа готовит в памяти 519 байт,
  но отправляет 518.
- `<выход>` — **номер физического разъёма DMX**: `F0` первый, `F8` второй,
  `F9` третий (модели USB1DMX / USB2DMX / USB3DMX). Это не «форматы», а выходы.
- Драйвер — стандартный FTDI CDM 2.12 (`Driver v2 12 FTDI.exe` из комплекта
  побайтово совпал с официальным FTDI CDM).
- Лицензию ключа проверяет сама FontanPlay по серийному номеру; интерфейс
  ничего не спрашивает, писать в него может любая программа.

### Тонкость Windows: когда появляется ftd2xx.dll

Установщик FTDI CDM только **кладёт пакет в хранилище драйверов**. Сама
`ftd2xx.dll` попадает в System32 лишь тогда, когда FTDI-устройство **первый раз
подключили** к этому компьютеру — в этот момент Windows доустанавливает драйвер
под конкретное устройство.

Отсюда два разных случая, которые важно не путать (программа их различает и
пишет разное):

| Случай | Что видно | Что делать |
|---|---|---|
| Драйвера нет вовсе | «драйвер FTDI не установлен» (красным) | поставить FTDI CDM, затем подключить интерфейс |
| Драйвер есть, устройство не подключали | «драйвер установлен; библиотека появится, когда подключите интерфейс» (жёлтым) | просто подключить интерфейс по USB |
| Есть только 32-битная (например, рядом с FontanPlay) | «нужен 64-разрядный драйвер» | поставить 64-разрядный CDM |

Наличие пакета определяется по хранилищу драйверов Windows
(`System32\DriverStore\FileRepository\ftdibus.inf_*`) — прав администратора не
требует.

### Почему у FontanPlay «третья вселенная налезает на первую»

Подтверждено в коде: FontanPlay **шлёт все три выхода (F0, F8, F9) каждый цикл
безусловно** — проверяет только флаг «устройство открыто», числа разъёмов
интерфейса она не знает. На USB1DMX/USB2DMX кадр F9 уходит в несуществующий
разъём, и прошивка, судя по симптому, кладёт его на выход по умолчанию —
первый. До конца проверяется только на железе.

В памяти самой FontanPlay раскладка верная: общая строка 1536 каналов режется
на 512 + 512 + 512 в отдельные буферы, наложения там нет.

**Вывод для нас:** слать только те выходы, что завёл пользователь (так и
сделано — один кадр на вселенную), и предупреждать в подсказке, что номер
выхода ставится по числу разъёмов на коробке.

Попутно найдена настоящая ошибка FontanPlay: процедура очистки строки DMX
обнуляет 1535 байт вместо 1536 — последний канал (он же последний канал третьей
вселенной) после сброса остаётся со старым значением. У нас вселенные
независимы и гасятся целиком.

### Соседние программы Musidora (нам не нужны)

- **FPCOM.exe** — «FontanPlay COM PORT Translator»: FontanPlay кладёт строку DMX
  в общую память (`Mapping=1` в FontanPlay.ini), FPCOM перекладывает её в
  обычный COM-порт. Их обходной мостик; к багу третьей вселенной отношения не
  имеет. Заодно доказывает, что интерфейс принимает данные и через COM — это наш
  запасной путь.
- **FPclient.exe** (Wi-Fi-приёмник) и **MusiWin7_10** (2017) — другие программы
  с чуть иной обёрткой кадра. Берём формат рабочего FontanPlay.

## Как это сделано у нас

Драйвер `packages/engine/src/drivers/musidora.ts` (ftd2xx.dll через koffi;
запасной путь — COM-порт). В «Настройках»: интерфейс (авто / серийный номер /
COM) и выход 1–3, **один формат кадра — выбора формата нет**. Под таблицей живой
статус: драйвер FTDI, найденные устройства, «кадры уходят» либо причина.

Самопроверка без железа:

```
npm -w @fountain-studio/engine run musidora-test
```

Проверяет кадр байт в байт против независимого эталона, снятого с
дизассемблера; обрыв кабеля и переподключение; занятость другой программой;
выбор по серийному номеру. Плюс загрузка настоящей ftd2xx64.dll, если задать
`FS_FTD2XX_DLL`.

**Не проверено:** на живом интерфейсе не запускалось ни разу — это делается
только на объекте (см. памятку `USB-DMX-проверка-на-объекте.md`).
