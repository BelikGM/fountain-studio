# Архитектура Fountain Studio

Название: **Fountain Studio** (утверждено 17.07.2026).
Статус: v0.3 — фазы 0 и 1 реализованы (§13–14).

---

## 1. Ключевое архитектурное решение: разделение на «Движок» и «Редактор»

Приложение с самого начала делится на два независимых процесса:

```
┌─────────────────────────────┐        WebSocket / IPC        ┌──────────────────────────────┐
│  РЕДАКТОР (UI)              │ ◄───────────────────────────► │  ДВИЖОК (Engine / Runtime)   │
│  React + TypeScript         │   команды, состояние,         │  Node.js worker / отдельный  │
│  таймлайн, секвенсоры,      │   поток DMX-кадров для        │  процесс с высоким           │
│  патч, 3D, аудио            │   визуализации                │  приоритетом                 │
└─────────────────────────────┘                               │  тик 50/25 мс, слои,         │
                                                              │  драйверы протоколов         │
                                                              └───────────────┬──────────────┘
                                                                              │
                                                     ┌────────────┬───────────┼────────────┬─────────────┐
                                                     │ Art-Net /  │ USB-DMX   │ RDM        │ Modbus TCP/ │
                                                     │ sACN (UDP) │ (serial)  │ (E1.20)    │ RTU (ПЧ)    │
                                                     └────────────┴───────────┴────────────┴─────────────┘
```

Зачем:
- **Точность тайминга.** UI (рендеринг, React, 3D) никогда не влияет на равномерность DMX-тика. Движок — маленький, без GC-давления, с предвыделенными буферами `Uint8Array[512]` на вселенную.
- **Автономная работа.** Движок может работать headless: автозапуск с Windows, расписание крутится без открытого редактора. Редактор подключается к уже работающему движку.
- **Путь развития.** Сейчас — сайт (UI в браузере + движок как Node-сервер), потом Electron (тот же UI + тот же движок внутри), потом при желании удалённый пульт с планшета — бесплатно, потому что связь уже по WebSocket.
- **Замена движка.** Если Node не хватит (не ожидается, см. §3), движок переписывается на Rust без изменений UI.

## 2. Варианты реализации (стек)

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| **A. Electron + Node-движок** ✅ рекомендую | UI: React+TS+Vite. Движок: Node.js в отдельном процессе. Упаковка: electron-builder → NSIS-инсталлятор | Один язык (TS) везде; лучшая экосистема для волновых форм/таймлайна/Three.js; путь «сайт → инсталлятор» прямой; `serialport`+`dgram` закрывают всё железо | Инсталлятор ~80–150 МБ; тайминг чуть хуже нативного (но с запасом достаточен, §3) |
| B. Tauri + Rust-движок | UI тот же, движок и оболочка на Rust | Максимальная точность тайминга, инсталлятор ~10 МБ, меньше RAM | Два языка, медленнее разработка, порог входа в Rust |
| C. Чистый сайт + локальный «мост» | UI в браузере, рядом маленький сервис-демон для железа | Ничего не устанавливать кроме моста | Это фактически недо-вариант A; браузер сам не умеет UDP/COM |
| D. Нативный (C#/WPF или Qt) | Классическое desktop-приложение | Зрелый RT на Windows | Медленная итерация UI, слабее инструменты для 3D/аудио-таймлайна |

**Рекомендация — A**, с оговоркой: движок пишем как отдельный пакет без зависимостей от Electron (чистый Node), тогда варианты C (мост) и headless-режим получаются автоматически, а миграция на B остаётся открытой.

Структура репозитория (monorepo):

```
aquascore/
├─ packages/
│  ├─ engine/        # движок реального времени (чистый Node/TS, без UI-зависимостей)
│  │  ├─ core/       #   тик-планировщик, слои, merge, компилятор шоу
│  │  ├─ drivers/    #   artnet, sacn, usb-dmx (enttec/ftdi), rdm, modbus
│  │  └─ server/     #   WebSocket API, headless-запуск, автозапуск по расписанию
│  ├─ shared/        # модель данных (типы, схемы, валидация) — общая для UI и движка
│  ├─ ui/            # React-приложение: таймлайн, секвенсоры, патч, 3D, аудио
│  └─ app/           # Electron-оболочка (main-процесс, упаковка, автообновление)
├─ fixtures/         # библиотека профилей устройств (JSON)
└─ docs/
```

## 3. Производительность: расчёт с запасом

Требование: 3 вселенные × 512 = **1536 адресов**, шаг ≤ 50 мс (≥20 Гц), равномерный.

- **Сеть (Art-Net/sACN):** кадр вселенной = один UDP-пакет ~570 байт. 3 вселенные × 20 Гц = 60 пакетов/с ≈ 34 КБ/с. Это ~0,003% гигабитной сети. Запас — тысячи вселенных. Даже 40 Гц (25 мс) — ничто.
- **USB-DMX (провод):** физика DMX512 — 250 кбод, полный кадр 512 каналов ≈ 23 мс → максимум ~44 кадра/с **на одну вселенную на один адаптер**. Для 3 вселенных по USB нужно 3 адаптера. Поэтому для мультивселенной правильное железо — **Ethernet-нода Art-Net/sACN** (1 коробка = 2–8 вселенных DMX-выходов), USB-адаптер остаётся как запасной/сервисный вариант.
- **Тайминг в Node:** дрейф-корректируемый планировщик (целевые моменты t₀+n·Δ, а не «setTimeout 50»), процесс движка отдельно от UI, повышенный приоритет процесса в Windows, предвыделенные буферы без аллокаций в тике. Реально достижимый джиттер — единицы мс при тике 25–50 мс; для воды и света это незаметно. Аудио-часы (позиция воспроизведения) — мастер-клок во время шоу, DMX-тик подстраивается под них, поэтому рассинхрона с музыкой не накапливается.
- Частота тика — настройка движка: 50 / 40 / 25 мс (20/25/40 Гц).

## 4. Протоколы

| Протокол | Назначение | Приоритет |
|---|---|---|
| **sACN (ANSI E1.31)** | DMX по сети, multicast, приоритеты источников, синхро-пакеты | Фаза 1 — основной |
| **Art-Net 4** | DMX по сети, де-факто стандарт нод; ArtPoll-обнаружение нод, ArtRdm | Фаза 1 — основной |
| **DMX512 по USB** | Enttec DMX USB Pro / Open DMX и совместимые FTDI-адаптеры (как у FontanPlay) | Фаза 1 |
| **RDM (ANSI E1.20)** | Обнаружение приборов, удалённая установка DMX-адресов, чтение сенсоров/ошибок. Требует адаптер с RDM (Enttec Pro и т.п.) или ноду с ArtRdm/RDMnet | Фаза 2 |
| **Modbus RTU/TCP** | Прямое управление частотными преобразователями насосов (уставка частоты, пуск/стоп, чтение аварий) — минуя DMX→аналог преобразователи | Фаза 2–3 |
| **OSC** | Интеграция с внешними пультами/медиасерверами, кастомные пульты (TouchOSC на планшете) | Фаза 3 |
| **MQTT** | Телеметрия/мониторинг фонтана (диспетчеризация), удалённые команды | Фаза 3 |
| RDMnet (E1.33), KiNET, SMPTE/MIDI timecode | По потребности | Резерв |

Драйверная модель: движок пишет в абстрактные «вселенные», каждой вселенной назначается один или несколько выходов (например, вселенная 1 → sACN universe 1 **и** USB-адаптер COM3 одновременно). Вход (AUX, внешний запуск) — тоже через драйверы.

## 5. Модель данных (доменная)

```
Проект (объект/фонтан)
├─ Настройки I/O: вселенные, ноды (IP), COM-порты, частота тика
├─ Библиотека профилей устройств (общая + локальная)
│    Профиль: имя, число каналов, роли каналов, семантика значений
│    Встроенные: Насос(1к, 0–255), Насос-ПЧ(1к + инерция), Клапан(1к, бинарный, порог),
│                Диммер(1к), RGB(3к), RGBW(4к), RGBA(4к), Мувинг-форсунка(Nк), Свой(Nк)
├─ Патч (адресация)
│    Устройство: профиль + вселенная + стартовый адрес + имя + группа/зона
│    Мастер авто-патча: «добавить N устройств профиля P с адреса A, шаг/порядок …»
│    Контроль коллизий адресов; карта адресов постранично (страницы с адресами)
│    Параметры устройства: мин/макс (калибровка «струя 10 мм … макс высота»),
│    кривая, инверсия, время инерции (для 3D и трекового опережения)
├─ Секвенсоры (количество — в настройках: 32 по умолчанию, до 256)
│    Секвенсор: имя, описание, клип каналов/устройств («скрепка»),
│    сцены (до 256), паттерны (диапазоны сцен со своей длиной и loop),
│    режимы: выключен / статика (держать сцену) / бег по сценам,
│    приоритет = номер (старший перекрывает), тип «импульсной» записи в буфер
├─ Пресеты/Макросы (≥32, число настраивается)
│    Статический = снимок значений; Динамический = набор запущенных паттернов
├─ Шоу (документ таймлайна)
│    ├─ Аудио: файл(ы), недеструктивные вырезки (мышью или вводом t_нач/t_кон),
│    │         громкость трека, волновая форма, маркеры
│    ├─ Дорожки управления (переменное число):
│    │    цель: устройство / группа / канал / секвенсор
│    │    события: огибающая 0–255 (рисование мышью), вызов сцены,
│    │             пуск/стоп/переключение секвенсора, импульс с удержанием,
│    │    смещение дорожки (± мс, опережение для инерции воды — на дорожку
│    │    и/или автоматически из инерции устройства), mute/solo, копирование
│    └─ Живая запись: клавиатура (клавиша=сцена/секвенция), мышь (уровень),
│         квантизация по долям, затем правка на таймлайне
├─ Плейлисты: список шоу; режимы: стоп в конце / трек в кольце / плейлист в кольце
├─ Расписание: строки {время, фильтры дата/день недели/месяц, действие:
│    OFF / PAUSE / ДИНАМИКА (без звука) / ШОУ / ПЛЕЙЛИСТ / МАКРОС n},
│    отдельно график подсветки; астрономический таймер (закат/рассвет) — опция
├─ Клавиатурные привязки: банки × наборы; клавиша → действие; запуск сценариев
└─ 3D-схема фонтана (см. §7)
```

Формат хранения: папка проекта (JSON-манифесты с версией схемы + аудиофайлы + кэш волновых форм + кэш компиляции шоу). Автосохранение + undo/redo в редакторе (в отличие от FontanPlay).

## 6. Движок: конвейер тика

Каждый тик (например, 25/50 мс) значение каждого адреса собирается из слоёв (снизу вверх, выше — приоритетнее):

```
0. База (всё в 0 / фоновая картина)
1. Режим расписания (OFF/PAUSE/ДИНАМИКА/…)
2. Таймлайн активного шоу (события дорожек, огибающие; часы = позиция аудио)
3. Секвенсоры (по приоритету номера; «импульсная» семантика — значение
   держится, пока не перекрыто)
4. Пресеты/макросы (вызванные вручную или с клавиш)
5. Живые ручные корректировки (виртуальные фейдеры, страницы адресов)
6. Пост-обработка на канал: мин/макс, кривая, инверсия
→ Кадры вселенных → драйверы (sACN/Art-Net/USB) + поток в 3D-визуализатор
```

- Шоу перед воспроизведением **компилируется** в индексированную по времени структуру — выборка событий за тик O(1), без поиска.
- Правила слияния настраиваемые: LTP (последний важнее — по умолчанию, как в FontanPlay) или HTP (максимум — классика для яркости света).
- Конец шоу — мягкое обнуление (как в FontanPlay), но настраиваемое (fade-out).

## 7. 3D-визуализация

Технология: Three.js (WebGL2, позже WebGPU), частицы струй на GPU.

- **Редактор схемы:** чаша (размеры/форма, несколько чаш, высоты горизонтов), коллекторы, форсунки (тип: прямая струя / веер / шатёр / цветок / вуаль / туман; наклон, поворот), прожекторы (позиция, направление, тип RGB/RGBW). Каждый элемент схемы связывается с устройством из патча.
- **Физика воды (правдоподобная, не CFD):** баллистика частиц (начальная скорость ∝ сглаженному значению насоса, гравитация, ветер — опция), **инерция**: значение насоса проходит через фильтр первого порядка с настраиваемыми временем разгона/спада (та самая задержка давления, под которую в треках делается опережение), распад струи на капли, пена/всплеск в точке падения (billboard-частицы), клапан = резкое отсечение с коротким «дожимом».
- **Свет:** RGB/RGBW-смешение во всём диапазоне, подводные прожекторы подсвечивают частицы струи (свет считается в шейдере частиц), bloom.
- Визуализатор ест **тот же поток кадров DMX из движка**, что и железо → превью честное. Режим **офлайн-превиза**: писать шоу «вдали от объекта» целиком в 3D (замена F3D.exe).

## 8. UI-принципы (ориентир — DAW/видеомонтаж/3D-пакеты)

- Единое окно с докируемыми панелями (как в Blender/Resolve/Ableton): Таймлайн, Секвенсор-грид (ячейки сцен, RGB-поле), Патч/Карта адресов, 3D-вид, Микшер (страницы фейдеров с адресами), Браузер проекта.
- Таймлайн: зум колесом, выделение мышью, точный ввод времени с клавиатуры, snap к долям/сетке, копирование блоков, перетаскивание, маркеры.
- Горячие клавиши на всё + режим «запись с клавиатуры» как в FontanPlay (перформанс-запись), банки клавиатур.
- Тёмная тема по умолчанию (работа у фонтана вечером).

## 12. Зафиксированные решения (ответы пользователя, 17.07.2026)

1. **Название:** Fountain Studio. **Стек:** вариант A (Electron + Node-движок + React). Протоколы — как в §4.
2. **Железо:** текущий адаптер неизвестен, пользователь готов заказать любой. Рекомендация — Art-Net/sACN нода (критерии в §4); USB-адаптер класса Enttec DMX USB Pro — как дополнительный/сервисный.
3. **RDM — назначение:** удалённый мониторинг состояния устройств из тех. помещения (устройство отработало неверно / пропало из линии). Значит: опрос сенсоров и статусов E1.20, индикация «жив/потерян/ошибка» на карте устройств, журнал событий. Реализация — фаза 2.
4. **Расписание и автономность:** запуск шоу по системному времени ПК; движок — headless-служба с автозапуском Windows и **watchdog-перезапуском** при падении/случайном закрытии (редактор — отдельно, его закрытие не влияет на работу фонтана).
5. **ОС:** Windows 10/11 приоритет; macOS возможен позже (стек кроссплатформенный, ничего не блокирует).
6. **Аудио:** mp3, обычная стереокарта. Формат .trk старой программы — проприетарный контейнер данных дорожек FontanPlay; у нас данные дорожек хранятся в открытом JSON рядом с аудиофайлом.
7. **Импорт из FontanPlay:** желателен, не критичен сейчас. Потребуются образцы файлов (.trk и файлы секвенсоров) для обратной разработки формата. Отдельная задача в фазе 3+.
8. **3D:** подтверждена важность. Ручное составление схемы до постройки фонтана: типы насосов, высота/толщина струи, адреса клапана/насоса/светильника, координаты, наклон; типы форсунок — обычные, пенные, ламинарные, рассеивающие, вариативные, вращающиеся по осям. **Импорт геометрии из AutoCAD — очень важно:** путь реализации — формат DXF (родной экспорт AutoCAD); для бинарного DWG — конвертация через ODA File Converter (бесплатный) или экспорт в DXF из AutoCAD. Плюс проигрывание готового трека в 3D.
9. **Насосы:** оба варианта на выбор в настройках проекта — DMX→аналог (как сейчас) и прямой Modbus к ПЧ. Общий принцип: функционал не «зашивается», а выбирается per-project.
10. **Тайминг:** базовый шаг 50 мс, приоритет — отсутствие пропусков и ошибок; возможность более частого шага заложена (сеть позволяет 25 мс; провод DMX ограничен ~44 Гц). Быстрее нужно в основном свету, вода инертна.
11. **Смещения дорожек:** подтверждено — вода должна запускаться раньше света: у каждой дорожки своё смещение (опережение), при этом на таймлайне дорожки отображаются и редактируются в единой временной сетке.
12. **Коммерция:** пока для себя. При продаже позже: лицензии/подписки и режим «только воспроизведение» (проект закрыт для редактирования — заказчик получает готовую программу без редактора). Архитектура движок/редактор это уже поддерживает.

## 15. Результаты фазы 2 «Шоу и звук» (17.07.2026)

Модель шоу (`packages/shared/src/show.ts`): звуковая дорожка + переменное число дорожек
управления на общем таймлайне. Время шоу — «смонтированное»: вырезки уже удалены из аудио,
блоки и огибающие ставятся по смонтированной шкале (перестановка вырезок сдвигает хвост, как
в видеомонтаже). Дорожки двух видов: **блоки** (сцена или секвенсор, растянутые на отрезок,
с фейдом ввода/вывода) и **огибающие** (значение одного канала устройства точками, линейная
интерполяция, рисование мышью). У каждой дорожки — `offsetMs` (опережение: вода читается
раньше света при одинаковой постановке на экране; отрицательное значение — запаздывание)
и `muted`.

Исполнение — в движке, стейтлес: позиция таймлайна однозначно определяет картинку, поэтому
перемотка и скраб мгновенно дают верное состояние DMX (включая шаг и фазу фейда секвенсора
внутри блока — вычисляются из elapsed, а не из накопленного состояния). Слияние всех дорожек,
блоков и огибающих — HTP. Мастер-часы — аудио редактора (Web Audio): движок экстраполирует
позицию между сообщениями `syncShow` (раз в 0.5 с) по своему тику; пауза/стоп/перемотка —
отдельные команды. Конец таймлайна — автопауза. Аудиофайлы хранит движок в `audio/` рядом
с проектом (`uploadAudio`/`getAudio` по WebSocket) — папка проекта переносима целиком.

Вырезки аудио: выделение мышью на волновой форме или числовой диапазон с клавиатуры;
хранятся по исходной шкале файла, помощники `editedToSourceMs`/`sourceToEditedMs`/
`keptSegments`/`mergeCuts` пересчитывают монтаж; воспроизведение склеивает куски
безразрывно (планирование `AudioBufferSourceNode` по сегментам). Вырезку можно
восстановить (недеструктивно).

UI (вкладка «Шоу»): таймлайн с линейкой и масштабированием, волновая форма (канвас по пикам,
вырезки схлопнуты), блоки таскаются и растягиваются мышью с прищёлкиванием к 0.1 с, точки
огибающих — двойной щелчок/перетаскивание/правая кнопка, панель свойств блока, счётчик
времени, горячие клавиши (пробел — пуск/пауза, Home — в начало). Курсор воспроизведения
ведётся через rAF без перерисовки таймлайна.

Проверка: `npm run smoke` расширен до 25 проверок — детерминированные стоп-кадры шоу по
перемотке (блок сцены, опережение клапана +1 с, шаг и середина фейда секвенсора в блоке,
HTP огибающей), автопауза в конце, тихая коррекция `syncShow`, монтажная арифметика вырезок,
байт-в-байт хранилище аудио. Пройден полностью.

Следующее: плейлисты и расписание (фаза 3), либо min/max-калибровка устройств и страницы
адресов в сценах, либо начало 3D (фаза 5) — по приоритету пользователя.

## 16. Принято в план: переадресация устройств (18.07.2026)

Ситуация с объекта: физически перепутаны или заменены приборы (светильник вышел из строя,
линии переставлены) — нужно из приложения переназначить адреса устройств относительно
изначальной схемы (в т.ч. построенной в 3D), не переписывая сцены.

Архитектура уже к этому готова: сцены, огибающие и секвенсоры привязаны к **устройству**
(deviceId), а не к DMX-адресу; адрес — свойство устройства в патче. Значит переадресация —
это операции над патчем, всё остальное следует автоматически:

- смена адреса/вселенной одного устройства (уже есть в патче);
- **обмен адресами двух устройств** («физически перепутаны») — одной кнопкой;
- **сдвиг диапазона** (вставили прибор в середину линии — хвост сдвинулся);
- переназначение профиля с пересчётом занимаемых каналов и контролем коллизий;
- в 3D (фаза 4): клик по прибору на схеме → его адресные свойства, подсветка
  «логический прибор ↔ физический адрес», режим «identify» (мигнуть прибором — через RDM).

Реализация — в блоке «доводка редактора» после фазы 3.

## 17. Принято в план: генерация сцен и ИИ-ассистент (18.07.2026)

Цель — не придумывать каждую картину вручную, а генерировать и дорабатывать. Записано
как фаза 6 (после 3D), потому что генераторам нужны геометрия фонтана из 3D-схемы и
аудиоанализ. Пункты от пользователя:

1. **Импорт готовых сцен по адресам** — записать в сцену значения для каждого адреса
   (снятие с внешнего источника/файла), измерение периода цикла T существующей сцены.
2. **Генерация новых сцен на основе старых** — вариации, инверсии, зеркала, сдвиги фаз.
3. **Генерация от фигуры фонтана**: программа знает геометрию (круг, квадрат, ромб,
   звезда, произвольная фигура из 3D/DXF) и раскладывает волны, бегущие огни, погони,
   симметрии по реальному расположению форсунок и светильников. Стили: спокойные,
   волнообразные, динамические, статические.
4. **Обучение на видео** масштабных фонтанных шоу (извлечение паттернов движения/цвета) —
   исследовательский пункт, дальний прицел.
5. **Аудиоанализ трека и автопостановка**: BPM (жанровые диапазоны темпа), громкость
   (RMS/пики), спектр по полосам, тишина. Правила: быстрый темп → быстрая смена картин;
   тихая спокойная музыка → низкие мягкие струи; громкость/бас → высота воды; форте →
   залпы. Результат — черновик шоу, гармонирующий с выбранным треком плейлиста,
   который человек дорабатывает на таймлайне.

Технически: BPM/спектр — Web Audio (OfflineAudioContext) или meyda/essentia.js в редакторе;
генераторы сцен — чистые функции над геометрией патча (детерминированные, с сидом);
«обучение на видео» — отдельный исследовательский спайк, не в основной ветке.

## 18. Результаты фазы 3 «Эксплуатация» (18.07.2026)

**Плейлисты** (`shared/playlist.ts`): последовательность шоу с паузами между ними (gapMs),
режимы «по кругу»/«один раз». Исполняет движок автономно: мастер-часы — тик движка
(в отличие от одиночного шоу, где мастер — аудио редактора). Битые элементы (шоу удалено)
пропускаются; ручное управление шоу из редактора (play/pause/seek/stop) перехватывает
воспроизведение у плейлиста, syncShow редактора при активном плейлисте игнорируется.

**Автономный звук**: `engine/audioplayer.ts` — системный плеер ffplay (бесплатный ffmpeg),
запускается движком на смену шоу в плейлисте; вырезки монтажа применяются фильтром
`aselect` — слышен тот же монтаж, что в редакторе. ffplay нет — предупреждение и шоу без
звука (вода/свет работают). Конфиг: `audio.player: auto|ffplay|none`, `audio.ffplayPath`.

**Расписание** (`engine/schedule.ts`): проверка каждые 0.5 с по системным часам ПК;
записи: время «ЧЧ:ММ[:СС]», дни недели (пусто — ежедневно), действие — плейлист/шоу/
секвенсор/сцена/стоп всё; защита от повторного срабатывания в ту же минуту.

**Служба**: `engine/tools/watchdog.ts` — сторож перезапускает движок через 5 с после
падения (проверено живым убийством процесса); `tools/install-autostart.ps1` — задача
планировщика Windows на вход в систему. Путь эксплуатации: ПК на объекте → задача
`FountainStudioEngine` → watchdog → движок → расписание → плейлисты со звуком ffplay.

UI: вкладки «Плейлисты» (элементы, паузы, транспорт ⏮/⏭/стоп, индикация текущего)
и «Расписание» (таблица записей: вкл, время с секундами, дни Пн–Вс, действие).

Смоук расширен до 31 проверки: последовательность плейлиста с паузой между шоу,
завершение «один раз», перехват редактором, живое срабатывание записи расписания
по системным часам, сохранение плейлистов и расписания в проект.

Следующее — «доводка редактора»: переадресация (§16 — обмен адресами, сдвиг диапазона),
min/max-калибровка устройств, страницы адресов в сценах, клавиатурные привязки; затем 3D (§7).

## 19. Результаты этапа «Доводка редактора» (18.07.2026)

для двух отмеченных (физически перепутанные приборы), «Сдвинуть адреса на ±N» для группы

**Клавиатурные привязки**: вкладка «Клавиши» — таблица «клавиша → действие → цель»,
захват физической клавиши (KeyboardEvent.code, не зависит от раскладки), действия:
сцена/секвенсор/шоу/плейлист (переключатели: повторное нажатие останавливает),
стоп всё, BLACKOUT. Глобальный диспетчер в редакторе: работает из любой вкладки, если
фокус не в поле ввода; локальные клавиши экранов (пробел на таймлайне) имеют приоритет.
Хранение — в проекте (project.keys), одна клавиша — одно действие.

Смоук — 35 проверок (добавлены: калибровка на живом выходе 200→168 при 50–200, ноль
остаётся нулём; swap/shift хелперы). Движок 0.4.0.

Следующее — фаза 4 «3D»: редактор схемы фонтана (типы форсунок, координаты, наклон),

насосам/клапанам/прожекторам в порядке адресов.

эмиссия ∝ сглаженному значению насоса — фильтр 1-го порядка с riseMs/fallMs (та самая
инерция давления, под которую в шоу делается опережение дорожек), закрытый клапан режет
струю быстрым спадом ~150 мс («дожим»). Баллистика: v0 = √(2g·H)·значение, гравитация,
у тумана — торможение воздухом; форма по типу (конус/веер в плоскости/кольцо шатра/цветок
с центральной струёй/вращение азимута). Цвет частиц — от привязанного прожектора
(RGB+W из кадра, диммер — белым), без света — тускло-голубая вода; смешение аддитивное.
Источник данных — те же DMX-кадры движка, что идут в железо (`frame` по WS уже был),
то есть честный офлайн-превиз: шоу пишется без выезда на объект (замена F3D.exe).

Смоук — 39 проверок (санитизация схемы с битыми ссылками, ringPositions, разбор DXF
с $INSUNITS, импорт по ролям слоёв с переводом мм → м). Проверено в браузере: кольцо
из 8 форсунок разных типов с RGB-подсветкой, струи и цвета живут от ручных значений
консоли. Three.js добавил ~570 КБ в бандл редактора — на движок не влияет.

## 21. Electron-упаковка (18.07.2026)

`packages/app` — настольное приложение. Архитектура прежняя, движок остаётся отдельным
процессом:

- **Главный процесс** (`main.cjs`, CommonJS без сборки): при старте проверяет порт 9520.

  `require('serialport')` в бандле остаётся внешним вызовом, резолвится из

  проблемы не имеет (чистый JS, ничего внешнего). Чистый Node — тот же файл

## 22. Фаза 5, часть 1: мониторинг сети Art-Net/RDM (18.07.2026)

Первая половина §12 п.3 (индикация «жив/потерян/ошибка» + журнал) — без железа,
против мок-ноды; полный опрос сенсоров E1.20 (ArtRdm GET SENSOR_VALUE, STATUS_MESSAGES)
отложен до покупки ноды с RDM.

**Движок** (`engine/netmonitor.ts`, движок 0.5.0): каждые 3 с шлёт ArtPoll на адреса
Art-Net-выходов из конфига; собирает ArtPollReply (имя ноды, выходные Port-Address).
Каждым вторым циклом — ArtTodRequest (по Net-группам вселенных проекта); из ArtTodData
извлекаются RDM UID приборов на линии. Нет ответа 10 с — нода «потеряна», прибор — 30 с;
возвращение фиксируется. Журнал — кольцо 100 событий. Ответы принимаются на сокет-
отправитель (unicast, так отвечает большинство нод) и на 6454 (reuseAddr, если порт
удалось занять) для нод, отвечающих broadcast'ом. Протокол WS: `network`-состояние
(ноды/приборы/журнал с ageMs) — при изменениях, раз в 3 с и при подключении клиента;
`refreshNetwork` — немедленный цикл опроса.

**UI**: вкладка «Сеть» — таблицы нод (статус/имя/IP/вселенные/последний ответ) и
RDM-приборов (UID производитель:устройство), журнал, кнопка «Обновить сейчас»;
пустые состояния объясняют, что нужна нода (дешёвые без RDM заполняют только список нод).

Смоук — 43 проверки: мок-нода в смоуке отвечает на ArtPoll/ArtTodRequest (ASCII-имена —
кириллица в Art-Net не кодируется), проверяются обнаружение, разбор TOD (2 UID),
журнал и потеря ноды по таймауту после «выдёргивания из сети».

Дальше по фазе 5: Modbus TCP для насосов с ПЧ (выбор per-device: DMX→аналог или
регистр ПЧ), затем полный E1.20-опрос при появлении железа.

## 23. Фаза 5, часть 2: Modbus для насосов с ПЧ (19.07.2026)

§12 п.9 реализован: у насоса в патче — выбор per-device, обычный DMX→аналог или
прямое управление ПЧ по Modbus. Марка ПЧ определилась из отдельного проекта
пользователя-конфигуратора (github.com/BelikGM/Modbus): **Elhart EMD-PUMP**,
дефолты полей — его карта регистров (8193/0x2001 — уставка частоты в сотых Гц,
8192/0x2000 — команда: 2=пуск, 1=стоп, 10 — код последней аварии F0.10 с
таблицей расшифровки в конфигураторе). Сам Fountain Studio ПЧ не настраивает —
только шлёт уставку/пуск/стоп от сцен и шоу и читает код аварии; тонкая
настройка привода — задача конфигуратора.

**Транспорта два**, оба реализованы (решение пользователя «оба сразу»):
- `engine/drivers/modbus-tcp.ts` — Modbus TCP (MBAP) на чистом node:net, для
  шлюзов RTU↔TCP; без зависимостей, тем же приёмом, что Art-Net/sACN;
- `engine/drivers/modbus-rtu.ts` — Modbus RTU по RS-485 напрямую через
  USB-адаптер (первая нативная зависимость движка — serialport; кадр
  адрес+PDU+CRC16 собирается вручную, `modbus-pdu.ts` — общие PDU/CRC16).
Общий интерфейс `ModbusTransport`; несколько насосов на одной шине/шлюзе делят
один транспорт (мультидроп RS-485), запросы сериализуются — один в полёте.

**`engine/pumpmodbus.ts` (PumpModbusManager)**: каждый тик получает значение
канала intensity насоса из того же итогового кадра, что уходит в DMX (т.е. после
HTP-слияния и калибровки; тест-паттерны тоже идут в ПЧ — пусконаладка). Запись
уставки — при изменении значения (троттлинг 200 мс) **плюс keep-alive раз в 1 с
без изменений**: у многих ПЧ вотчдог связи глушит привод без свежих команд, а
шоу может держать насос на одном значении десятки секунд. Код аварии опрашивается
раз в 3 с; статус (связь/уставка/авария/ошибка) идёт в UI сообщением `modbus`.

UI: в патче у насосов кнопка «ПЧ» — переключатель DMX/Modbus, выбор транспорта
(TCP: IP шлюза/порт; RS-485: COM-порт/скорость), unitId, регистры с дефолтами
Elhart, живой статус. Смоук: мок-ПЧ по Modbus TCP в том же процессе — уставка
39.22 Гц из канала 200, ПУСК/СТОП, повтор keep-alive, код аварии 7 доходит до
состояния. Всего проверок — 58.

## 24. Фаза 6, начало: генераторы сцен и аудиоанализ (19.07.2026)

Первые два пункта §17 (генерация от геометрии и аудиоанализ) — рабочие,
детерминированные, без ИИ-моделей:

**`shared/scenegen.ts`**: `layoutActors` (устройства с координатами из
project.layout по роли насос/клапан/свет), `invertScene` (255−v),

не нужно). UI — панель «⚡ Генератор» на вкладке «Сцены». Проверено в живом
браузере (Playwright + Chromium): кольцо из 8 форсунок → привязка насосов →
волна легла 128→218→255→218→128→37→0→37 по углам, секвенсор создан.

**`shared/audioanalysis.ts`**: чистые функции над PCM (Float32 моно + sample
rate) — `energyEnvelope` (RMS по окнам, нормировка к пику), `estimateTempo`
(автокорреляция онсетов, диапазон 70–180 BPM, сетка долей), `silenceRanges`,
`loudnessEnvelopePoints` (RMS → точки 0–255), `tempoCategory`. В редакторе —
кнопка «⚡ Автопостановка» на вкладке «Шоу»: downmix загруженного аудио,
черновая огибающая громкости на первое устройство с каналом intensity
(громкость → высота воды, §17 п.5), точки переводятся в смонтированную шкалу
(вырезки перепрыгиваются) и прореживаются; статус показывает найденный BPM.
Проверено в браузере на синтетическом клик-треке: 120 BPM определён точно,
огибающая повторяет громкость бёрстов. Оценка темпа — простая эвристика:
возможны октавные ошибки (60/240 вместо 120), человек правит на таймлайне.

**Импорт с линии и период цикла (§17 п.1)**: движок принимает входящий ArtDMX —
разбор OpDmx добавлен в слушающие сокеты монитора сети (`netmonitor.onDmx`),
`engine/dmxcapture.ts` держит кольцевой буфер ~2 мин кадров на вселенную
(Port-Address). Сценарий: старый контроллер вещает Art-Net на этот ПК (или его
софт направлен на IP ПК) — в панели генератора сцен: «Снять сцену с линии»
(кадр → значения устройств вселенной по адресам патча → новая сцена) и
«Измерить период цикла» — `shared/dmxcycle.ts::measureCyclePeriodMs`: поиск
lag с минимальной само-разностью кадров по «живым» адресам (мёртвые каналы
отбрасываются), пересэмплирование на сетку 100 мс, порог уверенности 0.3.
Проверено в браузере полной петлёй: секвенсор «бегущая волна» (12 шагов ×
150 мс) → Art-Net-выход движка → захват его же потока (конфиг на 127.0.0.1) →
измерение дало T ≈ 1.8 с с уверенностью 87%. WS-протокол: getDmxCapture /
measureDmxCycle → dmxCapture / dmxCycle. Смоук — 63 проверки.

Не начато из §17: «обучение на видео» (п.4 — исследовательский спайк).
Раскладка волн по фигуре добавлена: `radialWaveScene`/`radialWaveSequenceScenes`
принимают `mode: 'angle' | 'path' | 'line'` — по углу (круг), по обходу контура
равномерно по периметру (звезда/ромб/прямоугольник — не сжимается на коротких
сторонах, `actorPhases` считает длину хорд между соседями по обходу), вдоль
главной оси разброса (линейный фонтан, ось через ковариацию координат).
Проверено численно: для прямоугольника 20×2 отношение фазовых промежутков
длинная/короткая сторона ≈ 10 — совпадает с отношением длин сторон.

## 25. Находка при проверке: джиттер тика «отравлялся» одним сбоем навсегда (19.07.2026)

Во время браузерной проверки генератора сцен на dev-сервере, простоявшем
без перезапуска ~10 часов реального времени в этой сессии, в футере
обнаружились абсурдные числа: avg-джиттер порядка 16 000 000 мс. Причина —
`Ticker.stats()` считал `avgJitterMs` как `jitterSum / n` за всю жизнь
процесса. Headless-эксплуатация (§9, §18) держит движок сутками; один сбой
(сон Windows, зависшая проверка антивируса, что угодно, остановившее event
loop надолго) даёт один тик с джиттером в разы больше нормы — и при
миллионах уже накопленных тиков разбавить этот выброс обратно нечем: показание
avg остаётся бессмысленным буквально годами, хотя реальная работа давно
восстановилась. Это ломает единственный способ на глаз оценить качество
тайминга и в UI, и в консольном логе `[stats]` (index.ts, раз в 10 с) —
именно тот индикатор, на который смотрят при headless-эксплуатации на объекте.

Исправлено: `avgJitterMs` — экспоненциальное скользящее среднее (EMA,
α=0.01, `clock.ts::emaStep`, чистая функция), отражает недавнее поведение и
отходит от выброса за десятки секунд, а не годы. `maxJitterMs` осознанно
оставлен пожизненным максимумом — это другой вопрос («был ли сбой хоть раз»),
и его не нужно прятать. Смоук проверяет `emaStep` численно: после
катастрофического выброса (30 000 000 мс) среднее падает больше чем в 100 раз
за 500 тиков (≈25 с) и полностью приходит в норму (<10 мс) ещё за 600 тиков.

## 26. Шесть доработок по запросу пользователя (19.07.2026)

Одним заходом, по явному списку — «реализуй всё, что ниже, не переходи
дальше, пока не сделаешь». Итог: движок 0.6.0, смоук вырос с 43 до 92
проверок, всё реально прогнано (не только тайпчек) — сеть/UDP/TCP-протоколы
против моков, UI — в браузере через Playwright, включая один настоящий
сгенерированный видеофайл. Полная разбивка ниже; здесь — итог по каждому
пункту с указанием, что осталось непроверенным на реальном железе.

**1. Несколько вариантов протокола там, где нет единственного ответа.**
USB-DMX (протокол ENTTEC DMX USB PRO API поверх serialport, `drivers/
usb-dmx.ts`, третий тип DMX-выхода наравне с artnet/sacn), OSC
(`shared/osc.ts` + `engine/oscserver.ts`, UDP, пульты вроде TouchOSC,
project.oscBindings), MQTT (`engine/mqttclient.ts` + `mqttcontroller.ts`,
свой клиент 3.1.1 поверх node:net, телеметрия + команды,
project.mqttBindings). Общий диспетчер действий `RemoteAction`
(`shared/remote.ts`) переиспользуется OSC и MQTT. UI — вкладка «Удалённо».
Все включаются/настраиваются независимо в fountain.config.json, по
умолчанию выключены — лишнее не мешает, когда определится реальная схема
объекта. Проверено: OSC-сообщение по настоящему UDP и MQTT-команда с
мок-брокера (свой TCP-релей) реально меняют состояние движка в смоуке;
панель «Удалённо» проверена в браузере.

**2. Живая запись на таймлайн шоу.** Раньше не было реализовано — не
входило в объём предыдущих фаз (в §8 исходной архитектуры упоминалось как
идея, ни одна фаза явно не планировала). Теперь: «⏺ Запись» на вкладке
«Шоу» — клавиши из project.keys одновременно исполняются как обычно и
пишутся блоком в дорожку; вооружённые огибающие пишут точки с ползунка по
позиции плейхеда. Обнаружен и исправлен по ходу проверки в браузере баг:
глобальный обработчик клавиш в App.tsx сам вызывает `preventDefault()` при
штатном срабатывании — код записи ошибочно считал это признаком конфликта
и никогда не срабатывал.

**3. Универсальный слой RDM.** DEVICE_INFO, ярлыки, IDENTIFY (мигнуть),
DMX_START_ADDRESS (удалённая переадресация) — все параметры, обязательные
по спецификации E1.20 для любого прибора независимо от марки; опциональные
(сенсоры, статус-сообщения) сознательно не тронуты — их формат и факт
поддержки зависят от производителя, а марка светильников ещё не выбрана.
`engine/rdm.ts` + расширение `netmonitor.ts` (rdmRequest поверх уже
работающего сокета ArtPoll/TOD) + панель в «Сети». Проверено независимым
мок-ответчиком RDM (не переиспользует rdm.ts) — 7 проверок, включая
настоящую переадресацию GET(5)→SET(42)→GET(42) по UDP.

**4. Идея для «обучения на видео».** Настоящее обучение (перенос
хореографии из видео профессиональных шоу) — исследовательская ML/CV-задача,
не то, что можно спроектировать и реализовать за один заход без точного
запроса. Вместо этого — честный рабочий прототип попроще: извлечение
яркости и доминирующего цвета по кадрам (`shared/videoanalysis.ts` + `ui/
videoFrames.ts`), детерминированно, без нейросетей — ровно то, что
формулировка плана называла «паттерны движения/цвета». Кнопка «🎬 Из видео»
на вкладке «Шоу». Проверено не только на синтетических кадрах в смоуке, но
и настоящим видеофайлом: сгенерирован WebM (canvas+MediaRecorder,
чередование чёрный→белый→красный→зелёный) и скормлен реальной форме
загрузки — яркость на дорожке точно повторила чередование, вспышки легли
ровно на цветовые склейки.

**5. Аудиоанализ по максимуму.** К уже имевшимся BPM/громкости/тишине
добавлен спектральный слой: собственное БПФ (`fft()`, радикс-2, окно
Ханна), полосы частот (`bandEnergyEnvelope` — бас/средние/высокие,
настраиваемые), спектральный центроид («яркость» звука —
`spectralCentroidEnvelope`, на чистом тоне даёт центроид почти точно на
частоте тона), заметные всплески громкости (`peakEvents` — «форте →
залпы» из плана, не было реализовано, раньше была только непрерывная
огибающая без дискретных триггеров). «⚡ Автопостановка» при 2+ устройствах
с каналом intensity раскладывает громкость и высокие частоты по раздельным
дорожкам, плюс дорожка блоков «Форте → сцена». Проверено в браузере на
клик-треке: три дорожки легли автоматически, блоки залпов совпали с
кликами волновой формы.

**6. Драйверы — нужно ли что-то доустанавливать.** Ответ пользователю
(п.6 запроса): для разработки — нет, `serialport` подтягивает готовый
скомпилированный биндинг под Windows x64 сам, компилятор не нужен. Для
реального железа: Art-Net/sACN/Modbus TCP/OSC/MQTT — только по сети,
драйверов не требуют; USB-RS485/USB-DMX адаптер — Windows обычно ставит
драйвер сама (Silicon Labs CP210x/WCH CH340/FTDI), иногда нужно вручную с
сайта производителя чипа.

**Что осталось непроверенным на реальном железе** (честно, по каждому
пункту): USB-DMX — протокол реализован по спецификации, но ни разу не
касался настоящего адаптера (скорость порта 57600 — распространённое
умолчание, не гарантия); RDM — общий слой проверен мок-ответчиком, не
настоящим RDM-светильником; OSC — не проверялся с настоящим TouchOSC/другим
пультом, только собственным UDP-сообщением в смоуке; MQTT — не проверялся
с настоящим брокером (Mosquitto и т.п.), только с собственным мок-релеем;
аудио/видео-эвристики — на синтетике и одном сгенерированном ролике, не на
подборке реальных треков/видео с объекта.

## 27. Вывод кадров на линию: частота, обрыв потока, «пакеты наперёд» (13.09.2026)

Вопрос пользователя: как данные попадают на каналы, что будет при обрыве, как
часто можно слать и можно ли готовить пакеты наперёд.

Как сейчас работает (`engine.ts`, `tick()`):

- Кадр уходит **каждый тик и целиком** — все 512 каналов, без «отправляем
  только изменения». Так и надо: DMX512 — протокол *состояния*, приёмник
  держит последнее значение, а поток его подтверждает.
- Такт по умолчанию **50 мс (20 Гц)**, настраивается (`timing.tickMs`).
- Порядок слоёв: воспроизведение ⊕ ручная консоль (HTP) → калибровка приборов
  → ветровое ограничение насосов → служебный свет → **переадресация в самом
  конце**, уже над готовым кадром.

Выводы:

- **Потолок частоты — физика DMX512**, а не наш выбор: 512 каналов +
  стартовый байт на 250 кбит/с ≈ 23 мс на кадр, то есть **максимум ~44 Гц**.
  Art-Net и sACN рекомендуют ту же границу. Нынешние 20 Гц — половина потолка.
- **При обрыве потока «пустых адресов» не будет»:** узел держит последний кадр,
  у приёмника свой таймаут потери данных (обычно 1–2,5 с), а что он сделает
  дальше — удержит картину или погасит — зависит от прибора, не от нас.
  Насосы, скорее всего, **останутся на последней уставке** — это опаснее
  гашения (струя может остаться поднятой). Поэтому нужен failsafe на нашей
  стороне; сторож процесса `npm run engine:watchdog` уже есть.
- **Предрасчёт кадров наперёд** возможен, но **только для слоя
  воспроизведения**: сцены и секвенсоры детерминированы по времени. Ручная
  консоль, ветровое ограничение, служебный свет, калибровка и переадресация
  применяются в момент отправки — их предрасчитать нельзя, иначе фейдер
  оператора начнёт отставать на всю глубину буфера.
  - Память не ограничение: 512 каналов × 44 Гц ≈ 22 КБ/с на вселенную, час шоу
    ≈ 79 МБ; 10 секунд буфера — 220 КБ.
  - Реальное ограничение — **задержка реакции**: чем глубже буфер, тем позже
    шоу откликнется на стоп, фейдер, ветер. Разумно **0,2–0,5 с** (4–10 кадров).
  - Второе — **аудиосинхронизация**: буфер надо строить от часов аудио, иначе
    предрасчитанные кадры уедут относительно музыки на глубину буфера.
  - Итог: предрасчёт полезен не для «моментальности» (её даёт постоянная
    отправка, которая уже есть), а как защита от джиттера — короткая кольцевая
    очередь готовых кадров, которую отдельный таймер сливает ровным шагом.

Задачи, которые из этого следуют (failsafe, раздельный такт, буфер), —
в `IDEAS.md`. Про USB-DMX и интерфейс FontanPlay — в `USB-DMX.md`.

## 28. Отзыв офлайн-лицензии: почему это отдельный слой поверх подписи (17.09.2026)

Лицензия (см. `license.ts`) — подписанный Ed25519 файл, движок проверяет её
БЕЗ сети: осознанный выбор ради объектов, которые годами работают без
интернета. Из этого прямо следует: отозвать выданную подпись классическим
способом нельзя — файл с подписью не перестаёт быть подлинным оттого, что
продавец передумал. Значит, отзыв обязан быть ОТДЕЛЬНЫМ слоем, не частью
подписи, и обязан деградировать в «ничего не изменилось», если сети нет —
иначе отсутствие интернета на объекте выглядело бы как отозванная лицензия,
а это недопустимо для программы, которая держит фонтан.

Решение (`licenseRevocation.ts`):

- Издатель ведёт список отозванных ID компьютеров локально
  (`issue-license.ts revoke/unrevoke`, файл `revoked.json` рядом с
  приватным ключом — туда же, где журнал выпущенных лицензий).
- `export-revocations` печатает ИЗ него публичный файл без имён и пометок —
  только список ID. Его издатель выкладывает туда, куда сам решит (Gist,
  свой сайт — не наша забота, лишь бы отдавало статический JSON).
- Движок, если в `app-config.json` указан `license.revocationUrl`, раз в час
  скачивает этот файл и кэширует на диск (`revoked-cache.json` в данных
  программы). Без `revocationUrl` весь механизм выключен — ничего никуда не
  стучится.
- Неудачная попытка (нет сети, сервер лежит, битый JSON) **не трогает
  прежний кэш** — только успешный ответ замещает список целиком. Отсюда:
  отсутствие интернета никогда не выглядит как отзыв, а отмена отзыва
  (`unrevoke` + переопубликовать) реально снимает блокировку, как только
  движок в следующий раз дотянется до списка.
- `loadLicenseStatus()` проверяет отзыв ПЕРВЫМ, до подписи и срока: даже
  настоящая непросроченная лицензия не считается активной, если её ID в
  кэше отозванных.

Что сознательно не сделано: живого «мгновенного» отзыва нет и не может
быть при офлайн-модели — минимальная задержка равна следующему подключению
объекта к интернету плюс до часа (период проверки). Для того, что решаем
(прекратить обслуживать компьютер, который перестал платить или нарушил
условия), этого достаточно; мгновенное отключение работающего фонтана —
отдельная, гораздо более рискованная операция, которую сознательно не
встраивали в лицензионный слой.
