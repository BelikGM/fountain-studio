## 17.09.2026 — несохранённые правки при переключении, выбор папки, лицензии

**Зачем:** правки экрана «Проекты» по итогам живой проверки пользователем
(«Открыть другой проект» вместо непонятного «Объект из другой папки», кнопка
выбора папки — справа, при создании нельзя было указать, куда класть объект),
плюс безопасное переключение (раньше правка, не успевшая долететь до диска,
могла молча потеряться или молча сохраниться без спроса). Отдельно — учёт и
отзыв лицензий: три срока, имя компьютера, список отозванных.

- **Диалог о несохранённых правках.** У `ProjectStore` — `isDirty`/`discard()`.
  `openProject`/`createProject`/`copyProject`/`closeProject` теперь без
  `force` отказывают, если хранилище «грязное», и просят решить: «Сохранить и
  открыть/закрыть», «Не сохранять и…», «Отмена». Работает и при переключении
  из Проводника (двойной щелчок по `.fsproj`), не только с экрана «Проекты».
  Самопроверка: `npm -w @fountain-studio/engine run dirty-guard-test` (новая,
  22/22, поднимает настоящий движок и щёлкает по-настоящему — иначе диалог не
  проверить: сервер отвечает только тому клиенту, кто спросил).
- **Экран «Проекты» переработан:** «Открыть другой проект» (было «Объект из
  другой папки»), кнопка «Обзор…» — справа от поля пути; у форм «Создать
  проект» и «Сохранить как» — поле «Папка» с путём по умолчанию, который
  можно поменять (был жёстко зашит). У `closeProject` появился ответ об
  успехе (раньше — тишина, в UI зависал прошлый результат).
- **Попутно найдено и починено:** при совпадении имён объект получал папку
  «Новороссийск 2», но ВНУТРЕННЕЕ имя оставалось «Новороссийск» — в
  «Недавних» было не отличить два объекта с одинаковой подписью. Теперь имя
  всегда берётся от итоговой папки. Нашлось через собственный скриншот сцены
  с двумя одноимёнными объектами.
- **Учёт и отзыв лицензий** (`issue-license.ts`): добавлен пробный срок (30
  дней) — теперь `trial`/`year`/`forever`; имя компьютера отдельно от имени
  покупателя (`--device` при выпуске, `rename` — переименовать позже);
  `list` показывает всё разом и отмечает отозванные. Отзыв: `revoke`/
  `unrevoke` — локально у издателя (`revoked.json` рядом с ключом, не публично),
  `export-revocations` — публикуемый файл без имён, только ID. Движок
  (`licenseRevocation.ts`) сам подтягивает этот файл раз в час, если в
  `app-config.json` указан `license.revocationUrl`; без него ничего не делает.
  Неудачная попытка (нет сети) не трогает прежний кэш — офлайн никогда не
  выглядит как отзыв. `loadLicenseStatus()` проверяет отзыв раньше подписи и
  срока. Разбор решения — `ARCHITECTURE.md` §28. Самопроверка:
  `npm -w @fountain-studio/engine run license-test` (21/21, живой HTTP-сервер
  в тесте — успех/недоступность/мусор/снятие отзыва).

**Проверено:** typecheck, build, smoke, все самопроверки (включая новые
dirty-guard-test и license-test). Экран «Проекты» снят своими скриншотами —
подписи влезают, диалог появляется по-настоящему при живом клике «Открыть».
CLI лицензий прогнан вручную на изолированной тестовой папке ключей (issue
trial/year/forever, list, rename, revoke, export-revocations, unrevoke) — все
команды отработали. Реальный `license-keys/` пользователя не трогали.

**Не проверено:** отзыв лицензии на живом объекте с реальным интернет-каналом
(revocationUrl ещё не настроен ни на одном реальном движке — публиковать
список отозванных пока негде, это решение продавца, не техническое).

## 17.09.2026 — несколько объектов на одном компьютере

**Зачем:** до сих пор проект был ОДИН на установку — второй фонтан заводился
только через экспорт/импорт архива. Теперь объект — это папка, их сколько
угодно, и переключаются они на ходу.

- **Раскладка данных разведена на две части** (как в VS Code и Unity: рабочее
  место отдельно, проект отдельно):
  - объект — самодостаточная папка `Документы\Fountain Studio\Проекты\<Имя>\`:
    `project.json` (схема, приборы, сцены, шоу, расписание), `lines.json`
    (вселенные, протокол, номера выходов, шаг тика), `audio\`, `logs\`,
    `backups\`, файл-ярлык `<Имя>.fsproj`;
  - настройки самой программы — в `%APPDATA%\Fountain Studio`: недавние
    объекты, лицензия, `fountain.secrets.json` с токеном Telegram. **Токен
    специально НЕ в папке объекта**: папку отдают коллеге, токен отдавать нельзя.
- **Движок умеет менять объект на ходу** — `packages/engine/src/projects.ts` и
  переписанный `index.ts`. Перезапуск не нужен: хранилища (`ProjectStore`,
  `AudioStore`, `AudioPlayer`, `BackupStore`, `NetworkMonitor`,
  `TelegramNotifier`, журнал) научились `rebind` на другую папку, сервер держит
  те же объекты всю жизнь процесса. Линии применяются ДО проекта — калибровка и
  насосы на Modbus индексируются по вселенным.
- **Четыре способа открыть объект:** экран «Проекты» при запуске (недавние,
  свежий под Enter), кнопка в шапке из работающей программы, двойной щелчок по
  `.fsproj` в папке объекта, аргумент `--project <папка>` (им же пользуется
  автозапуск: `tools\install-autostart.ps1 -Project "<папка>"`).
- **Одна копия программы на компьютер:** `app.requestSingleInstanceLock()` —
  вторая копия передаёт путь первой и закрывается. Иначе два движка заняли бы
  порт 9520 и стали двумя хозяевами на одной линии DMX.
- **Экран «Проекты»** (`ProjectsView.tsx`): недавние с путём и датой, пропавшие
  папки помечены, выбор папки обычным окном Windows, создание, «Сохранить
  как…» (копия объекта без журнала и бэкапов — это история исходного), закрытие
  объекта. Идёт шоу — перед переключением спрашиваем.
- **Переезд со старого расклада:** прежний `fountain.project.json` копируется
  (не переносится!) в `Проекты\<имя>\` при первом запуске новой версии. Порядок
  выбора при старте: `--project` → последний открытый → переезд → демо-объект.
- **Починено попутно:** линия без `outputs` роняла движок на
  `u.outputs.map(...)` — то есть шоу на объекте вставало из-за одного неполного
  поля в файле, который правится руками. Добавлена проверка `linesUsable()`, она
  же прикрыла импорт архива и `updateConfig` по сети.
- **Ключ лицензий убран из git** (`packages/engine/license-keys/` в
  `.gitignore`, `private.pem` снят с учёта). Сам файл на диске остался.

**Проверено:** `typecheck`, `build`, `smoke`, `projects-test` 55/55,
`musidora-test` 67/67, `failsafe-test` 14/14, `eventlog-test` 11/11,
`telegram-test` 17/17. Сверх того — живая проверка на изолированной папке
данных (рабочие файлы не трогались): 37 проверок, ноль ошибок — первый запуск,
создание второго объекта, раздельные линии, переключение без перезапуска,
закрытие, перезапуск с тем же объектом, `.fsproj`, копия, битые настройки,
`--project`. Экран «Проекты» снят своими скриншотами в двух видах (объект
открыт / объект не открыт) — подписи влезают, обрезки нет.

**Не проверено:** на живом железе ничего из этого не гоняли — нужен объект.

## 16.09.2026 — совместная разработка, аварийное отключение, журнал на диске, Telegram

**Зачем:** к разработке подключается второй человек со своей машины; заодно
закрывали самое опасное из открытого списка.

Сделано:

- **Аварийное отключение (failsafe)** — раньше не было вообще. Движок следит,
  что кадры реально уходят на линию: если такт вставал или выход не доставляет
  дольше заданного времени (по умолчанию 10 с), насосы и клапаны принудительно
  уходят в 0, свет — по настройке. Вывод восстановился — движок сам вернулся к
  обычной картине. Настройка в проекте, состояние видно в «Настройках», уходит
  в журнал и Telegram. Проверка: `failsafe-test` (14/14).
  Важно: закрытие редактора аварией НЕ считается — шоу играет движок.
- **Журнал событий на диске** — был только в памяти и терялся при перезапуске.
  Теперь `logs/events-ГГГГ-ММ-ДД.jsonl` рядом с проектом, по файлу на сутки,
  хранение 60 дней; переживает перезапуск, нумерация продолжается, битая строка
  после обрыва питания чтение не роняет. Проверка: `eventlog-test` (11/11).
- **Telegram**: «✅ Восстановлено» при возврате узла/прибора/ПЧ на связь; тихий
  режим на 1/4/8 часов на время работ (аварии молчат, «Восстановлено» приходит
  всегда, по окончании — строка «смолчали N аварий»); имена приборов из патча
  вместо голых RDM-UID (привязка — на вкладке «Диагностика», поле `rdmUid` у
  прибора). Проверка: `telegram-test` (17/17).
- **Умолчания вывода**: новый объект заводится с ОДНОЙ линией на протоколе
  `USB-DMX (FountanPlay)`; добавленная линия повторяет протокол предыдущей и
  получает следующий номер разъёма.
- **Экспорт/импорт проекта теперь везёт и настройки линий DMX** — перенесённый
  на другой компьютер объект больше не остаётся немым.
- Диагностика драйвера FTDI: различаем «драйвера нет вовсе» (красным, надо
  ставить) и «драйвер есть, интерфейс ни разу не подключали» (жёлтым, это
  нормально) — Windows кладёт `ftd2xx.dll` только при первом подключении.
- Документы: заведены `CLAUDE.md` (правила и порядок сдачи) и этот журнал;
  `IDEAS.md` перестроен под список задач, разборы вынесены в `USB-DMX.md` и
  `ARCHITECTURE.md` §27.

Не сделано / следующее:

- **Несколько проектов на одном компьютере** — первый пункт в `IDEAS.md`, там
  же развёрнутое описание того, что должно получиться.
- Проверка USB-DMX на живом интерфейсе — ждёт версии, которую не стыдно отдать
  тестировщикам на объект.

## 15–16.09.2026 — вывод на интерфейс FontanPlay (USB-DMX)

- Разобран протокол USB-интерфейса из комплекта FontanPlay (дизассемблером
  рабочей версии 1.9.2.4 с объектов пользователя). Кадр на один выход: 518 байт,
  `FF FF FF <выход> 00 <512 каналов, 255→254> FF`; `<выход>` — номер физического
  разъёма DMX (F0/F8/F9). Детали — `docs/USB-DMX.md`.
- Сделан выход «USB-DMX (FountanPlay)»: драйвер через `ftd2xx.dll` (koffi),
  запасной путь — COM-порт; в «Настройках» выбор интерфейса и выхода, под
  таблицей — живой статус (драйвер, устройства, «кадры уходят» либо причина).
  Проверка без железа: `musidora-test` (67/67).
- Найдено, почему у FontanPlay «третья вселенная налезает на первую»: она шлёт
  все три выхода безусловно, не зная числа разъёмов интерфейса. Мы шлём только
  заведённые выходы, в подсказке предупреждаем.
- Не проверено на живом интерфейсе — только на объекте.
